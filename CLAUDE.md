# Project guidance for Claude Code

This repository is an AI-run revenue business (YouTube first). **Read `docs/MANAGEMENT_PRINCIPLES.md` first**; it is the permanent operating principle.

**Session continuity (permanent rule, owner directive 2026-11-26): this is NOT a new project each chat.** Before any work read, in this order: this file -> `docs/MANAGEMENT_PRINCIPLES.md` -> `docs/PROJECT_STATE.md` (current state + index to all source material) -> `docs/DECISIONS.md` (currently valid owner directives and why they changed) -> `docs/SESSION_PROTOCOL.md` (start/end procedure) -> the tail of `docs/SESSION_LOG.md`. Do not repeat research, development or verification that already exists; do not ask the owner to re-explain. Save results as you go and update these files at the end of every session.

Key rules (details in that file):
- The goal is a self-running loop of experiments -> publish -> measure -> diagnose -> improve, not "a great video" or "one viral hit".
- Plan from human desires with evidence (competitor URLs, dates, views, subscriber counts; unverified = "未確認"); the AI chooses and justifies the plan, the owner is not asked to judge scripts.
- Every video is an experiment with an ID, hypothesis, cost and later metrics; separate failure causes (impressions / CTR / early drop-off / expectation mismatch); change few things at a time.
- Never report unfinished work as finished. Measured values and estimates are labelled separately.
- Owner approval is required for: new spending or budget changes, account creation, publish permissions, the first public release. Budget: about 30,000 JPY per month.
- Keep existing assets (code, DB, workflows); do not rebuild without checking them first.
- Secrets are never printed. Code lives on the working branch; tests must pass.

## Directive of 2026-11-26 (permanent, second): turn accumulated knowledge into management capability
- Information, analysis, stored knowledge and code are NOT the end point. The goal is a better-operating AI business entity: better decisions, product planning, marketing, sales and problem solving after a year than today. Distinguish 8 stages and never call a DB row a capability: (1) acquire (2) understand (3) analyse success/failure factors (4) extract general knowledge (5) apply to another problem (6) validate in the real market (7) update knowledge from results (8) autonomous decision and re-execution.
- Capability claims need evidence: pre-registered criteria, same model/task/budget, with-knowledge (B) vs without-knowledge (A) comparison, independent blind evaluation (preliminary only; market response and economic results are the final test), tests on industries/problems NOT used in the research, and no unfounded scores or completion percentages. Keep comparable test records (`docs/CAPABILITY_LOG.md`, `experiments/ablation/`) so model/knowledge/tool effects can be separated where possible.
- Failures are decomposed (product, customer choice, appeal, price, awareness, acquisition path, funnel, trust, production quality), measured facts are separated from cause hypotheses, reusable assets are identified, and continue/modify/withdraw is decided by comparing retry value and cost; useful lessons go into the knowledge DB.
- Learning loop: research -> knowledge -> plan -> run -> measure -> cause analysis -> knowledge update -> next decision, recorded per experiment (knowledge used, why, expected effect, actual result). Do not increase knowledge count as a goal; expire or correct wrong knowledge.
- Do not delay market experiments for capability tests; reuse existing code/data (no large new systems); research cap 2,000 JPY, monthly 30,000 JPY and all approval conditions stay.
