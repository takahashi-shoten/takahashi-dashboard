## 段階
### 段階1(実施済み・非破壊): 同一リポジトリで、文書と記録を分ける
- `docs/projects/`(索引)、`docs/projects/beauty_sns/`(引き継ぎ・分離案・開始用の文)、`docs/BUDGET_LEDGER.md` を追加。既存ファイルの移動・削除はなし。
- 子のClaudeは、作業ブランチを `claude/beauty-*` の接頭辞で作る(親は従来どおり)。
### 段階2(承認が必要): 非公開の新リポジトリ(例: `ai-beauty-sns`)
- 目的: 顧客・店舗情報、撮影素材、見積・契約、毎週の数字を、公開リポジトリから隔離する。
- 共通技術の使い方(いずれか): (a) `studio/` を、親から `git submodule` で取り込む (b) `pip install git+https://…@タグ` で固定バージョンを使う (c) 親に直接PR。**推奨は(b)**(バージョンを固定でき、重複開発にならない)。
- 作成は、オーナーが行う(私の道具では、リポジトリの新規作成と、他リポジトリへの書き込みはできない)。新リポジトリを、Claudeのセッションに接続する設定も、オーナーの操作。
### 段階3(必要になったら): ワークフローの分離
- いまの `key-check.yml` に、美容用のtask(kitsuke*、kimonorefs)が同居。新しいworkflowファイルは、mainに存在しないと手動実行できないため、**PRのmainへのマージ(承認事項)が前提**。段階2の新リポジトリに、独自のworkflowを置く方が簡単。
### 採らない案
- 全コピー(完全分離): 共通技術が重複して、改善が両方に反映されない。
## 親への還元の仕組み
- 子 → 親: 週1回、`RETURN_TO_PARENT.md`(知識・販売実績・成功と失敗・技術改善)。親は、セッション開始時に確認して、知識DBに取り込む(仮説は仮説のまま)。
- 技術改善: 共通コードの変更は、テストを通して、親のブランチへ。
- 親 → 子: 親の方針変更(予算・承認・情報管理)は `CLAUDE.md`/`DECISIONS.md`。子は、セッション開始時に確認する。
## 親の継続
- 親は、美容業界に固執せず、世界中の収益機会の探索(`docs/research/opportunity_ranking_2026-11-26.md`)、市場調査、自律収益化システム(調査→実験→公開→測定→改善)の構築を、従来どおり続ける。親の優先は、子の作業を待たない。
